# Trace-Derived Metrics — Service Graph (Environment-Anchored)

> **Inventory status**: Confirmed present in live VictoriaMetrics inventory (2026-07-06).
> **Source component**: Tempo metrics-generator (service_graphs processor).
> **Span metrics**: NOT emitted in this environment — see dedicated section below.

In this environment, the **only** trace-derived metrics are **service graph** metrics produced by Tempo's metrics-generator. These represent edges (client → server relationships) in the service dependency graph and provide per-edge RED signals (Request rate, Error rate, Duration).

---

## Architecture: How Service Graph Metrics Are Generated

```
App (AlwaysOnSampler)
  → OTel Agent Collector (per-node)
    → OTel Gateway Collector (tail sampling here — otelcol_processor_tail_sampling_* confirmed present)
      → Tempo (ingest)
        → Tempo metrics-generator [service_graphs processor]
          → remote_write → VictoriaMetrics
```

The metrics-generator inspects ingested traces and pairs client/server spans (by trace ID + span ID parent relationship) to emit per-edge metrics. It buffers spans in an in-memory store until the corresponding pair arrives or a TTL expires.

**Key implication**: Since this runs **post-tail-sampling**, the metrics reflect only the sampled trace population (biased toward errors and high-latency). See [Sampling Bias](#sampling-bias-critical-caveat) below.

Source: [Tempo service graphs docs](https://grafana.com/docs/tempo/latest/metrics-from-traces/service_graphs/)

## Service Graph Metrics (Confirmed Present)

All metrics below are confirmed present in VictoriaMetrics as of 2026-07-06. Labels on all: `client`, `server`, `connection_type`.

### `traces_service_graph_request_total`

| Field | Value |
|-------|-------|
| **Type** | Counter |
| **Unit** | requests |
| **What it measures** | Total count of requests between two service nodes (one edge in the graph) |
| **Labels** | `client`, `server`, `connection_type` |
| **Troubleshooting use** | Per-dependency request rate; topology discovery; traffic volume per edge; detect unexpected dependencies |

Verified: [Tempo docs](https://grafana.com/docs/tempo/latest/metrics-from-traces/service_graphs/) — "Total count of requests between two nodes".

### `traces_service_graph_request_failed_total`

| Field | Value |
|-------|-------|
| **Type** | Counter |
| **Unit** | requests |
| **What it measures** | Total count of **failed** requests between two service nodes (span `status_code = ERROR`) |
| **Labels** | `client`, `server`, `connection_type` |
| **Troubleshooting use** | Per-dependency error rate; cascading failure detection; pinpoint which downstream is failing |

Verified: [Tempo docs](https://grafana.com/docs/tempo/latest/metrics-from-traces/service_graphs/) — "Total count of failed requests between two nodes".

### `traces_service_graph_request_server_seconds_bucket` / `_count` / `_sum`

| Field | Value |
|-------|-------|
| **Type** | Histogram |
| **Unit** | seconds |
| **What it measures** | Request duration as seen by the **server** (time the server span was active) |
| **Labels** | `client`, `server`, `connection_type`, `le` (bucket boundary) |
| **Troubleshooting use** | Server-side latency per edge; isolate whether slowness is server-internal or network/sidecar |

Verified: [Tempo docs](https://grafana.com/docs/tempo/latest/metrics-from-traces/service_graphs/) — "Time for a request between two nodes as seen from the server".

### `traces_service_graph_request_client_seconds_bucket` / `_count` / `_sum`

| Field | Value |
|-------|-------|
| **Type** | Histogram |
| **Unit** | seconds |
| **What it measures** | Request duration as seen by the **client** (time the client span was active — includes network transit + sidecar overhead) |
| **Labels** | `client`, `server`, `connection_type`, `le` (bucket boundary) |
| **Troubleshooting use** | Client-perceived latency; when compared to server_seconds reveals network/sidecar/mesh overhead |

Verified: [Tempo docs](https://grafana.com/docs/tempo/latest/metrics-from-traces/service_graphs/) — "Time for a request between two nodes as seen from the client".

## Labels Reference

| Label | Values | Meaning |
|-------|--------|---------|
| `client` | service name (from `service.name` resource attribute) | The service initiating the request |
| `server` | service name or virtual node name | The service receiving the request |
| `connection_type` | `""` (empty/unset), `virtual_node`, `messaging_system`, `database` | Type of connection between nodes |

### `connection_type` semantics (from Tempo docs)

| Value | When set |
|-------|----------|
| (empty) | Direct service-to-service (client span kind=CLIENT, server span kind=SERVER) |
| `virtual_node` | One side is uninstrumented (missing client or server span) — synthetic node |
| `messaging_system` | Producer→consumer via message queue (span kind=PRODUCER/CONSUMER) |
| `database` | Client span with `db.namespace`, `db.name`, or `db.system` attributes present |

### ⚠️ Cardinality Considerations

| Risk | Source | Mitigation |
|------|--------|------------|
| 🟡 Medium | `client` × `server` grows as O(N²) with service count | Monitor `tempo_metrics_generator_registry_active_series`; use `filter_policies` to exclude noisy edges |
| 🔴 High | Custom `dimensions` added to service graph config | Avoid or use only very low-cardinality attributes |
| 🟢 Low | `connection_type` | Fixed enum (4 values) |

## Tempo Metrics-Generator Health Metrics (Confirmed Present)

These internal Tempo metrics monitor the health of the metrics-generator itself:

| Metric | Type | What it measures | Troubleshooting use |
|--------|------|------------------|---------------------|
| `tempo_metrics_generator_registry_active_series` | Gauge | Current number of active time series produced by metrics-generator | Cardinality monitoring; capacity planning; detect explosion |
| `tempo_metrics_generator_registry_series_limited_total` | Counter | Series that were rejected because the active series limit was hit | Non-zero = **losing topology data**; increase `max_active_series` or reduce dimensions |
| `tempo_metrics_generator_spans_received_total` | Counter | Total spans received by the metrics-generator | Throughput; confirm generator is receiving data |
| `tempo_metrics_generator_processor_service_graphs_expired_edges` | Counter | Edges that expired (TTL hit before pair arrived) | High count = broken context propagation, spans arriving too late, or TTL too short |

## How Metrics Interrelate (Correlation)

| Relationship | What it reveals |
|-------------|-----------------|
| `client_seconds_p99 - server_seconds_p99` for same edge | Network + sidecar (Istio ztunnel/waypoint) overhead. Positive delta is expected; large delta = mesh/network problem |
| `request_failed_total / request_total` per edge | Per-dependency error rate — the RED "E" per edge |
| High `expired_edges` + normal `spans_received_total` | Spans arriving but **not pairing** — context propagation broken (missing `traceparent`) or one side not instrumented |
| `series_limited_total` rising + `active_series` at ceiling | Metrics-generator at cardinality limit — edges being silently dropped; review dimensions or add filter_policies |
| Edge A→B has high error rate, AND B→C also shows errors | **Cascading failure**: B is failing because C is failing. Trace the chain to root cause |
| Edge A→B shows in graph but B→C is **missing** | B→C communication lacks context propagation (uninstrumented service between B and C) |
| `client_seconds` spike but `server_seconds` flat | Problem is NOT in the server — it's network latency, DNS, sidecar (Istio), or connection pooling on client side |
| `server_seconds` spike but `client_seconds` proportional | Problem is server-internal (slow DB query, CPU, GC) |
| `connection_type="virtual_node"` with `server=user` | External traffic entering the mesh from an uninstrumented client (browser, external API caller, cron job) |

## Symptom → Metric Quick-Reference

| Symptom | MetricsQL Query | What to look for |
|---------|-----------------|------------------|
| **Which downstream is failing for service X?** | `sum(rate(traces_service_graph_request_failed_total{client="X"}[5m])) by (server)` | Highest error-rate edge → that's the failing dependency |
| **Per-edge error rate (ratio)** | `sum(rate(traces_service_graph_request_failed_total{client="X", server="Y"}[5m])) / sum(rate(traces_service_graph_request_total{client="X", server="Y"}[5m]))` | Ratio > 0.01 = investigate |
| **Server-side p99 latency per edge** | `histogram_quantile(0.99, sum(rate(traces_service_graph_request_server_seconds_bucket{client="X", server="Y"}[5m])) by (le))` | Compare against SLO threshold |
| **Network/sidecar overhead** | `histogram_quantile(0.99, sum(rate(traces_service_graph_request_client_seconds_bucket{client="X", server="Y"}[5m])) by (le)) - histogram_quantile(0.99, sum(rate(traces_service_graph_request_server_seconds_bucket{client="X", server="Y"}[5m])) by (le))` | Positive value = network+mesh overhead in seconds |
| **Cascading failure — top error edges** | `topk(10, sum(rate(traces_service_graph_request_failed_total[5m])) by (client, server))` | Trace from leaf to root — deepest server with errors is likely the root cause |
| **Topology: all edges from service X** | `sum(rate(traces_service_graph_request_total{client="X"}[5m])) by (server, connection_type)` | Discover all downstream dependencies |
| **Topology: who calls service X?** | `sum(rate(traces_service_graph_request_total{server="X"}[5m])) by (client)` | Discover all upstream callers |
| **Database edge latency** | `histogram_quantile(0.95, sum(rate(traces_service_graph_request_server_seconds_bucket{server="Y", connection_type="database"}[5m])) by (le))` | Slow DB queries visible as high server_seconds on database edges |
| **Metrics-generator dropping data?** | `sum(rate(tempo_metrics_generator_registry_series_limited_total[5m]))` | Non-zero = series limit hit; losing edges |
| **Context propagation broken?** | `sum(rate(tempo_metrics_generator_processor_service_graphs_expired_edges[5m]))` | High rate = edges timing out (spans not pairing) |
| **Generator receiving traces?** | `rate(tempo_metrics_generator_spans_received_total[5m])` | Should be positive and stable; drop = upstream issue |
| **Cardinality explosion** | `tempo_metrics_generator_registry_active_series` | Compare against configured limit; rising fast = new dimension or chatty service |

## MetricsQL / PromQL Query Examples

### Per-edge error rate for all dependencies of a service

```promql
# Error rate for every downstream of "orders-api"
sum(rate(traces_service_graph_request_failed_total{client="orders-api"}[5m])) by (server)
/
sum(rate(traces_service_graph_request_total{client="orders-api"}[5m])) by (server)
```

### Client-perceived p99 latency per edge

```promql
histogram_quantile(0.99,
  sum(rate(traces_service_graph_request_client_seconds_bucket{client="frontend", server="orders-api"}[5m])) by (le)
)
```

### Network + sidecar overhead (client minus server latency)

```promql
# Positive result = overhead added by network/Istio/sidecar between A and B
histogram_quantile(0.99,
  sum(rate(traces_service_graph_request_client_seconds_bucket{client="A", server="B"}[5m])) by (le)
)
-
histogram_quantile(0.99,
  sum(rate(traces_service_graph_request_server_seconds_bucket{client="A", server="B"}[5m])) by (le)
)
```

### Top-5 slowest edges by server-side p95

```promql
topk(5,
  histogram_quantile(0.95,
    sum(rate(traces_service_graph_request_server_seconds_bucket[5m])) by (le, client, server)
  )
)
```

### Requests per second through an edge

```promql
sum(rate(traces_service_graph_request_total{client="checkout", server="payment-service"}[5m]))
```

### All database edges and their latency

```promql
histogram_quantile(0.95,
  sum(rate(traces_service_graph_request_server_seconds_bucket{connection_type="database"}[5m])) by (le, client, server)
)
```

## Sampling Bias — CRITICAL Caveat

⚠️ **These metrics are generated POST-tail-sampling** (at Tempo metrics-generator, which only sees sampled traces). Tail sampling in this environment (`otelcol_processor_tail_sampling_*` confirmed present at the gateway collector) preferentially retains:

- 100% of error traces
- 100% of high-latency traces
- Probabilistic % of normal traces (varies by environment)

**Consequence**: Service graph metrics are **biased toward errors and slow requests**. Error rates will appear HIGHER than reality. Latency percentiles will skew HIGH.

### What this means in practice

| Use case | Valid? | Why |
|----------|--------|-----|
| Topology discovery (which services talk to which) | ✅ YES | Edges exist regardless of bias |
| Relative comparison (edge A slower than edge B) | ✅ YES | Bias is uniform across edges |
| Cascading failure detection (which edge fails) | ✅ YES | Errors are 100% captured |
| Network overhead (client - server delta) | ✅ YES | Delta cancels out absolute bias |
| Absolute error rate as SLI/SLO source | ❌ NO | Inflated by sampling bias |
| Absolute latency percentile as SLI | ⚠️ CAUTION | Skewed high; use SDK-level HTTP metrics for SLI instead |
| Trend detection (was it slower yesterday?) | ✅ YES | If sampling policy is stable |

**For unbiased SLI/SLO**, use OTel SDK application metrics (`http.server.request.duration`, `http.client.request.duration`) which see 100% of traffic — see skill `apm-metrics-cross-runtime`.

### `span_multiplier_key` (debiasing, if configured)

Tempo supports `span_multiplier_key` — a span/resource attribute containing the sampling ratio. When set, the metrics-generator scales counts by 1/ratio. If NOT configured (check your Tempo config), raw counts are underestimates of actual traffic volume.

## Grafana Visualization

The Grafana **Service Graph / Node Graph** panel uses these metrics to render the topology. Configuration requirement:

- Tempo datasource must have `serviceMap.datasourceUid` pointing to the VictoriaMetrics datasource holding `traces_service_graph_*` metrics.
- The node graph displays: nodes (services), edges (connections), with error rate and latency overlaid on each edge.

## Span Metrics (NOT Currently Emitted in This Environment)

> ⚠️ `traces_spanmetrics_*` metrics are **NOT present** in VictoriaMetrics as of 2026-07-06. This section documents what they WOULD provide and how to enable them, for future reference.

### What span metrics provide (that service graph doesn't)

| Capability | Service Graph | Span Metrics |
|-----------|---------------|--------------|
| Per-operation RED (by `span_name`) | ❌ | ✅ |
| Error rate per specific endpoint | ❌ | ✅ |
| Latency distribution per operation | ❌ | ✅ |
| Fan-out / N+1 detection | ❌ | ✅ |
| Per-dependency view (edge-level) | ✅ | ❌ (aggregated by service) |
| Network overhead diagnosis | ✅ | ❌ |

### Metric names (if enabled)

From Tempo metrics-generator `span_metrics` processor:

- `traces_spanmetrics_calls_total` — Counter — total span count per (service, span_name, span_kind, status_code)
- `traces_spanmetrics_latency_bucket`/`_sum`/`_count` — Histogram (seconds) — span duration distribution
- `traces_spanmetrics_size_total` — Counter (bytes) — total size of ingested spans

### How to enable

In Tempo configuration (`metrics_generator` section):

```yaml
metrics_generator:
  processor:
    span_metrics:
      enable_target_info: true
      dimensions:
        - service.name
      # Avoid adding high-cardinality dimensions (user_id, request_id)
```

Then remote_write to VictoriaMetrics. Caution: span_name cardinality can explode if services have untemplated HTTP routes.

### Pre-sampling alternative (unbiased SLI)

For unbiased span metrics valid as SLI sources, deploy the OTel Collector `spanmetrics` connector **before** the tail-sampling gateway:

```
App → Agent Collector [spanmetrics connector HERE] → Gateway (tail sampling) → Tempo
                          ↓
                    VictoriaMetrics (unbiased RED per operation)
```

This requires collector pipeline changes and is not currently deployed.
